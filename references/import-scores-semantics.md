# 「导入成绩」接口的真实语义 + 导入结果核对法（2026-10-01 实测）

> 本文只记**实测事实**（附证据），供下次少走弯路。凡未坐实的都标「推测」。

## 1. 接口

```
POST /v2/tasks/import/data/    multipart/form-data
  usernamePrefix = ""          （学生姓名前缀，留空）
  source         = "qt"        （qt=全通教育 zhx=智学网 dameijia=达美嘉
                                haofenshu=好分数 haofenshuMiniTable=好分数-小分表）
  taskId         = <taskId>
  file           = <xlsx>
成功 → 响应体 `{}`；有错 → 响应体是非空对象（行/列级错误映射）
前端组件 `fl-task-import`（chunk-P7ZFKARA.js）：`importTaskData(file, usernamePrefix, source, taskId)`
页面说明原文：「上传**阅卷系统导出**的答题详情。同时上传多个班级成绩时，确保文件名中包含完整的班级名称。」
```

**导入是后台异步**：接口返回 `{}` 只是「已提交」，真正的结果看**左下角消息**。

## 2. 导入结果核对：看左下角消息（不是看页面）

```
GET /v2/inbox/trainer/?page=N        ← page 必须走 params，不能拼进 path（拼进去会 400 Auth Error 1002）
```
通知 title = `导入任务数据`，content 形如：
```json
{"success": {"历史.xlsx": "导入学生: 39"}, "error": {}, "title": "历史.xlsx"}
```
- **成功文案只有「导入学生：N」——不含任何分数信息。**
- 报错样例（真实抓到过）：
  - `{"success":{},"error":{"分数格式错误[行,列]":"[4,I]、[4,J]…"}}` → 分数格格式不对（整批被拒）
  - `{"success":{},"error":{"学生班级未找到":"张三、李四…"}}` → 班级对照表里的学生对不上
  - 换 source 时：`{"未能解析出班级":["历史.xlsx"]}` → 该 source 期望文件里有「班级」列/字段

## 3. ⚠️ 核心结论：qt 导入写入的是「学生名单」，不是分数

**实测（2026-10-01）**：对 105 个任务导入后，用 `snapshot_scores.js` 抓导入前后全量指纹，**323 个任务逐格 diff 零变化**：
`score` / `finishAt` / `hasPhoto` / `id` 全为空。→ **导入只把学生挂到任务上，没有写入任何分数。**

**已排除的因素**（都试过，均无效）：
- 签名 / taskId / 等待时间（30s ~ 4h）
- 文件格式：① 交付原文件（openpyxl，inlineStr + 数字 `t="n"`）
  ② 转 sharedStrings（字符串 `t="s"`）③ **完全复刻学校成功文件的格式**（字符串 `t="s"` + 数字**无 `t` 属性**）
- 数据源：`haofenshuMiniTable` / `haofenshu` / `dameijia`（这三个直接报「未能解析出班级」）
- 任务软删除状态（已 recover 的任务同样写不进）

## 4. 站内「分数」从哪来：答题卡

判据（`GET /v2/tasks/<id>/score/`，每个学生一条）：
| 字段 | 含义 |
|---|---|
| `score` | 总分（>0 = 有分） |
| `finishAt` | 作答/提交时间（有值 = 有作答记录） |
| `hasPhoto` + `photos[]` | **答题卡照片**（`100tifen.com` 域名） |
| `id` | 作答记录 id（null = 无作答记录） |
| `markedBy` | `[{"markBy":"系统"}]` = 系统识别/阅卷 |
任务级（`GET /v2/tasks/?subjectId=<sid>&gradeId=<gid>&type=2&page=N`，返回体是 **`results`** 字段）：
`finishCount` / `studentCount` / `markPercent` / `correctPercent`。

**2026-10-01 全站盘点（465 个任务）**：有分数的**只有 60 个** =
**化学 51 + 英语 4 + 地理 2 + 政治 3**；其余学科全 0。
- 化学 51 个：`markPercent=0` + `correctPercent` 有值（未经阅卷）
- 英语/地理/政治：`markPercent=100` + `markedBy=[{"markBy":"系统"}]`（阅卷/识别产生）
- **共同点：所有有分数的学生都带答题卡照片 `hasPhoto=true`** ⇒ **分数伴随答题卡数据**，xlsx 导入不可能产生照片。

## 5.1 ⚠️ 队列必须与「上传对照清单」条数对账（2026-10-01 漏传事故）

**事故**：首批上传队列 105 条，而对照清单列的是 108 条 —— 差 3 条
（`2026-2027第一学期高三8月开学联考` 的 **英语 / 地理 / 政治**）。
文件都在交付目录里、内容完整、站内任务也都存在，**只是没排进队列**，且 `upload_task_scores.js`
的日志是 `ok=105 fail=0` —— **从脚本输出完全看不出漏了**（漏的是"没被排进来"，不是"排进来后失败"）。
用户是靠肉眼发现"英语数量比别人少"才问出来的。

**根因**：交付目录 → 上传队列 这一步的匹配是独立实现，与生成对照清单的实现在两条路径上，
两者没有交叉校验。

**约定**（以后每次上传前必做）：

```bash
# ① 从交付目录枚举"应传"集合（剔除用户指定跳过的学科，如化学）
# ② 从 items.jsonl 枚举"实传"集合
# ③ 断言两个集合相等，差集非空就停下来核对，不许直接上传
# 实测口径：应传 = ✅组文件数 − 指定跳过学科数；实传 = items.jsonl 行数
```

- 断言要按 **(考试, 学科)** 配对做，不是只比总数（总数相同也可能错配）。
- 上传**完成后**再用同一配对重算一次：`实传集合 == 应传集合`。
- 交叉验证看**消息栏条数增量**：`GET /v2/inbox/trainer/` 的 `count`
  上传前记一次、上传后应为 `前值 + 本次条数`（本次 145 → 148）。`count` 是对账的唯一硬指标，
  因为通知文案只有文件名没有考试名，同名科目分不出来。
- ⚠️ 这也解释了为什么"看日志全绿"不等于"传全了"：**绿只证明排进队列的执行成功了**。

## 5.2 ⚠️ 平台拒收「有空格的小题分」——整份文件作废（2026-10-01 实测）

**现象**：`{"success":{},"error":{"分数格式错误[行,列]":"[4,I]、[4,J]、…"}}`，
`success` 为空 ⇒ **一名学生都没导入**（不是"部分成功"）。

**实测归因（2026-10-01 均摊版 8 份上传，2 份中招）**：被点名的格子**恰好就是空着的那些**——

| 文件 | 报错格数 | 行 | 列 |
|---|---|---|---|
| 2024-2025第二学期高一期中·英语 | 405 = **5 行 × 81 列** | 68,104,105,106,107 | I…CK（全部题号列） |
| 2024-2025第一学期高一期中·英语 | 2916 = **36 行 × 81 列** | 4,5,67,68,70–84,91–107 | I…CK（全部题号列） |

- 空行数 = 该文件「源表没有小题分」的学生数（5 / 36），**逐行对得上**；
- 空列数 = 模板全部题号列，说明这些学生**整行小题分皆空**；
- **一个非空单元格都没被点名** ⇒ 判据是「**单元格为空**」。

**结论**：模板 `小题分` 表里**任何一个题号格留空，整份文件都会被拒**。

### 5.2.2 ⚠️ `upload_task_scores.js` 的幂等会静默漏传（2026-10-02 实栽）

脚本的幂等是 `done = log 里 ok:true 的 taskId`，而 `ok:true` 只表示**接口返回了 `{}`（已提交）**，
**不代表平台收下了**。实测 `17104084` 在 `avg8/log.jsonl` 里就是 `ok:true`，而平台侧是
`分数格式错误[…]`、一名学生都没导入。

⇒ **凡是导入结果是看 inbox 回执才知道的（本接口全是），re-run 就得换新的 log 文件**，
否则脚本会打 `SKIP — 已在 log 中成功过` 并静默跳过，日志还显示 `fail=0`。
做法：给每批用带批次标识的新 log（如 `log_<考试>_<学科>_<日期>.jsonl`），
**别复用上一批的**。上传完再用 §5.4 的 `inbox_receipts.js` 核对，别只看 `fail=0`。

⚠️ **区分两个作用域，别把规矩用错了地方**（2026-10-02 校准）：

| 作用域 | 规矩 | 出处 |
|---|---|---|
| **交付文件 / 原文件**（`✅完全没问题/`、`⚠️待人工检查/`、`🟢合并列均摊版/`） | **一个格子都不许动**：不许删行、不许给空格填 0、不许把总分均摊进题号格 | 用户 10-01 规矩：「有总分但小题全空 = 问题数据，绝不删」 |
| **专门为上传做的「剔除版」副本** | 可按用户口径把「缺小题分」的学生**整行连姓名删掉**（视作缺考），再上传 | 用户 10-02 口径 |

做法（10-02 实际跑通，6 份 6/6 成功）：**先把原文件整份备份 → 再在副本上删 → 删完备份留着，
源数据到手后仍可原样补传**。脚本 `exam-upload-template-fill/scripts/absent_prune.py`
（幂等、自动备份）；删完必须过 `precheck_upload.py`（空格 = 0）才传。
原文件与副本**分开存放**，别在同一份文件上原地改。

> 起因：平台收下文件的**必要条件**是「小题分表里凡有姓名的行，题号格都不为空」（§5.2）。
> 想让平台收下 → 只能在**上传副本**上剔除那些行；不想动数据 → 就照 §5.3 那样**不传 + 记录**。
> 两条路都合法，**由用户选**，不要自作主张。


**连带效应**：这条也解释了为什么「⚠️待人工检查」那批（源表有学生级缺口）当初没传 —— 传了也一定是全份被拒；
而按 §5.3，这批**不补也零损失**，无需为此删人填 0。

**上传前自检**（务必加进队列生成）：

## 5.3 ⚠️ 被拒收 = **零可观测损失**（2026-10-01 实测；结论：不要为「让平台收下」而改数据）

同一批 8 份上传里，6 份回执 `导入学生: N`、2 份 `分数格式错误[…]`。把**成功件**与**被拒件**
在站内逐项对比，**找不到任何以「导入成功」为条件的差异**：

| 观测点 | 接口 | 成功（17104065） | 被拒（17104084） | 判定 |
|---|---|---|---|---|
| 每生成绩记录 | `GET /v2/tasks/<id>/score/` | 31 条，`score/id/finishAt/hasPhoto` 全空 | 31 条，**逐条与成功件完全相同**（JSON 串比对 `true`） | 无差异 |
| 任务学生数 | `GET /v2/tasks/?subjectId=…` 的 `studentCount` | 31 | 31 | 无差异 |
| 任务详情 | `GET /v2/tasks/<id>/detail/` | 19 个字段 | 差异只有 `id/title/examId/exercise(试卷)/taskPackId` —— **全是任务固有属性，无导入痕迹** | 无差异 |

- `studentCount` 的真实语义 = **班级人数**，与导入无关（实测：2024级 9班=31 / 10班=34 / 18班=39 / 19班=12，
  同班所有任务取值恒定）。**不要**拿它当"导入了多少人"的证据。
- 与 §3 的结论自洽：qt 导入连**名单**也没落到这些接口上（323 任务逐格 diff 零变化）。
- 前端也没有列出"已导入学生"的接口（`/v2/tasks/<id>/students|student|data|import/` 全 404）。

**因此**：文件被拒时，**正确的收尾是记录 + 报告，不是改数据**。
「去掉缺失行」「给空格填 0」「把总分均摊进题号格」都**换不来任何站内变化**，只会污染交付文件
或制造推定数据。要判断"导入到底有没有生效"，看 `GET /v2/inbox/trainer/` 的**回执文案**即可。

## 5.4 正确读 inbox 回执（否则会误判"没有这条记录"）

> ✅ **别手写这段解析了** —— 已沉淀为成品脚本，坑全部做成了机制：
> ```bash
> node scripts/inbox_receipts.js [--limit N] [--since <UTC时间>] [--grep <考试名>] [--expect N] [--out f]
> ```
> 退出码：`0` 通过 / `3` 有拒收回执 / `4` `--expect` 不符 / `5` 凭据失效（401）。
> 2026-10-02 首次全量跑：168 条导入回执里 **6 条失败**（3 条 `分数格式错误`、
> 1 条 `学生班级未找到` 列出 20 名学生、1 条 `缺少题号`）—— 说明**历史上有多份从未真正导入成功**。

四个必须知道的细节，少一个就会得出错误结论（2026-10-02 复盘时踩过）：

1. **`content` 是「双层转义」的字符串**。`x.content` 取出来长这样：
   `{"success": {"2024-2025\u7b2c\u4e00\u5b66\u671f...": "\u5bfc\u5165\u5b66\u751f: 116"}}`
   —— 中文是**字面 `\uXXXX` 转义**，不是汉字。所以：

   ```js
   // ❌ 恒 false —— 会把"明明存在的回执"判成不存在
   String(x.content).includes('第一学期高一第1次月考')
   // ✅ 解两层：先脱外层转义，再 JSON.parse（解析出的中文仍是 \uXXXX，需再解一层才可 includes）
   const dec = s => {
     let t = String(s);
     for (let i = 0; i < 2; i++) {
       try { const v = JSON.parse('"' + t.replace(/"/g, '\\"') + '"'); if (typeof v !== 'string') return v; t = v; }
       catch { break; }
     }
     return t;
   };
   const obj = JSON.parse(dec(x.content));
   ```

2. ⚠️ **成功/失败的判据是「`error` 里有没有内容」，不是「`success` 是否为真」**。
   解码后的结构是 `{success: {文件名: "导入学生: N"}, error: {}, title: 文件名}` ——
   **被拒收时 `success` 是空对象 `{}`**，而 `error` 才有内容：

   | 回执 | 含义 |
   |---|---|
   | `{"success":{"英语.xlsx":"导入学生: 116"},"error":{}}` | ✅ 成功导入 116 人 |
   | `{"success":{},"error":{"分数格式错误[行,列]":"[4,I]、[4,J]…"}}` | ❌ **整份拒收，一名学生都没导入** |

   ```js
   // ✅ 唯一正确写法
   const bad = j.error && Object.keys(j.error).length > 0;
   // ❌ 写 if (j.success) → 被拒收时 success 是 {}，会被误判成「成功」（10-01 那份英语就这么漏过）
   // ❌ 只扫顶层键 → 成功时的文件名/人数在 j.success 里，会把 168 条全判成失败
   ```

3. **时间字段叫 `createAt`**（不是 `createdAt`/`createTime`），ISO 字符串带 `+00:00`（UTC），
   比北京时间**小 8 小时** —— 直接当本地时间读会差一天。

4. **靠文件名区分"是谁传的"**（用于判断某条回执是否本批作业所为）：

   | 文件名形态 | 来源 |
   |---|---|
   | `语文.xlsx` / `物理.xlsx`（**纯学科名**） | **我们交付目录**的命名法 |
   | `<考试名> <学科>班级对照表.xlsx`（可能带 ` (1)`） | **平台 `/task/import` 页下载的原件**，即**别人**在操作 |

   例（2026-10-02）：`2024-2025第一学期高一第1次月考 语文班级对照表 (1).xlsx`
   ⇒ 是学校/他人自行下载模板后上传的，**不是我们那批**。

> 对账硬指标仍是 `count` 增量（§5.1）；本条解决的是"**回执内容归属**"——想确认某格到底被谁导过时用。

## 5.5 学科实体被「删除重建」的识别法（用于判断"是不是别人动了这一格"）

同一格（考试 × 学科）看起来没变，实则被别人推倒重来时，有三条独立指纹：

| 指纹 | 怎么读 | 判定 |
|---|---|---|
| **`examSubjectId` 变了** | `GET /v2/exam/<examId>/subjects/` 的 `id` | 与历史快照不同 ⇒ 该学科实体被重建 |
| **旧 esId 直接 404** | `GET /v2/exam/subject/<oldEsId>/marker/` | `404 No ExamSubject matches the given query.` ⇒ 旧实体已删 |
| **id 号段跳档** | 同场其他科都在连续号段（如 10298x–10311x），某一科却远在天边（如 103583） | 该科是**后来新建**的 |

补充：`/v2/tasks/` 里该格任务的 `deletedAt` 被**刷新到今天**，也是重建痕迹
（平台在重建/重导时会重建任务对象）。

⚠️ **判定出"别人在动"之后的动作只有一个：停手 + 报告**。不改、不统一参数、不"顺手补一刀"。

### 5.5.1 怎么发现"本机还有另一路操作在同时跑"

2026-10-02 实操发现：同一个交付目录 / `/tmp` 工作区 / 生产站，可能**同时有另一路（另一个会话或人工）在写**。
动手前用这三条扫一遍（都是只读）：

1. **目录 mtime**：`find <交付目录> -maxdepth 1 -newermt "<今天 00:00>"` ——
   出现**你没建过的**文件/目录、且时间戳落在**你本次工具调用窗口内**，就是并发。
2. **inbox 最新回执的文件名命名法**（§5.4 第 3 条）——
   出现 `…班级对照表.xlsx` 这类**平台原件命名**，而我方是纯学科名 → 不是我方所为。
3. **自己的工作区**：`find /tmp/fuulea -newermt "<刚才>" -type f` ——
   冒出你不认识的脚本/`items.jsonl`/`log.jsonl`，就是另一路在建队列。

**风险**：两路同时写同一生产站 → **重复导入 / 互相覆盖 / 对账口径打架**。
**处置**：自己立刻停手（只读），在报告里明确列出并发证据与风险，建议**同一时间只保留一路在写**。

**分发上的连带注意**：技能目录本身也可能被那一路改动
（如 `SKILL.md` 被"对方的实现"顺手改过）→ 交付前**重读一遍**要引用的技能文件，
别按记忆里的旧版讲。
